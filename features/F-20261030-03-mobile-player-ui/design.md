# 移动端玩家 UI 设计方向

日期：2026-10-30。状态：待后续设计与实现；仅沉淀方向，不是当前实现规范。

需求和边界见 [feature.md](feature.md)。当前实现事实仍以[游戏页面规范](../../docs/spec/presentation/game-view.md)及实际代码为准。

## 1. 核心原则

**放开 UI 的边界，不放大整套 UI。**

保留原版风格、视觉密度和游戏构图。场景的固定坐标、UI 的设计基准比例、控件允许使用的区域是三件事，不能把“UI 不受场景画布裁剪”理解为“按未经缩放的设计字号铺满屏幕”。

此前整套界面改用原始逻辑字号显示的方案已被用户否定并撤回。本次不恢复该方案，也不沿用它的界面截图、测试通过记录作为新设计的验收证据。

## 2. 当前基线

- [PlayerView](../../src/Presentation/GalNet.Avalonia.GameHost/Views/PlayerView.axaml) 当前通过默认 1920x1080 的 GameCanvasHost 承载整个 GameShell。
- [GameCanvasHost](../../src/Presentation/GalNet.Avalonia.Controls/GameCanvasHost.axaml) 当前使用 Viewbox 等比缩放，画布里的字体、间距和按钮也随之缩放；设计字号不等于最后显示的实际字号。
- [GamePage](../../src/Presentation/GalNet.Avalonia.GameView/Page/GamePage.cs) 拥有场景、对白、NVL、选项和历史控件，主题负责安排布局。未来调整不能创建第二套 presenter 或破坏原有挂载、输入和释放契约。
- 三套主题各有布局特点，不能把 Classic 的底栏安排直接覆盖到 Minimal 或 Paper。

后续开始设计时重新采集当前原版基线，并记录源码版本、窗口逻辑尺寸、显示缩放和方向，不将本记录中的基线描述当作永久不变的实现假设。

## 3. 目标布局

| 部分 | 方向 | 必须保留 |
| --- | --- | --- |
| 桌面页面 | 以原版为视觉基准，不做触屏式全局放大 | 原有字号比例、留白、菜单宽度、对白高度及工具栏位置 |
| 场景层 | 固定剧情坐标、等比显示，允许留黑 | 背景、立绘、动画和场景效果的定位、比例与合成语义 |
| 阅读层 | 优先让对白可利用画布外的安全可用空间 | 原有低矮、横向舒展的形态，不改成厚重大卡片 |
| 控制层 | 底部操作条可越过场景边界，手机减少常驻操作 | 桌面完整工具栏、原有命令和状态反馈 |

“越过画布”不是无限铺满：对白仍需合理的左右边距和阅读宽度上限。桌面普通比例下应与原版基本一致；超宽屏只使用必要的额外空间，不把正文拉成难以阅读的长行。

首轮只研究对白和操作条的边界。NVL、选项、历史和其他页面不因拆分层级而自动改布局；确有适配需要时单独确认。

## 4. 手机局部调整

### 对白

- 先试验让正文相对当前手机实机效果增大约 15%-20%，姓名略调，其他文字基本不动。
- 该区间是对照稿试验值，不是已确认的最终参数，也不是全局界面缩放系数。
- 只为正文可读性增加必要空间，避免同时放大字号、内边距、对白高度和周围空白。
- 保留原版配色、透明度、边框和排版气质。常用对白长度、长中文行和姓名较长的情况一起检查，不只展示空白框或短英文。

### 底部操作条

- 手机首轮建议常驻“自动、快进、历史、更多”一排；最终项目和顺序由对照稿确认。
- 存读档、设置、截图、返回标题及隐藏 UI 等其余命令通过“更多”保留可发现的入口，不只依赖隐藏手势。
- 桌面不采用这套收纳，不删减现有完整工具栏。
- 保持轻量文字按钮的视觉风格。可适当扩大透明点击区，但不要求同步画出巨大的按钮背景。
- 增大的命中区不能互相覆盖或遮挡正文；点底栏、菜单和返回操作不能同时推进剧情。
- 自动/快进的激活状态、不可用状态、历史可用性和本地化标签应继续正确展示。

### 设置等普通页面

- 留到游戏页视觉方向确认后再做，沿用原分类、配色和控件风格。
- 只在空间不足时上下排列标签与编辑器，操作绑定行按实际可用宽度换行。
- 优先减少多余空白、解决溢出，不全局放大按钮，也不重新包装成一套大卡片。
- 页面切换、调整布局或打开下拉框不能清空文字、丢失设置状态或遗失正在录入的绑定。

### 安全区域与方向

背景可以延伸，正文、底栏、菜单和返回操作避开刘海、挖孔及系统手势区域。不要在多层容器重复扣除安全边距。

先以普通横屏和超宽横屏明确设计。竖屏的完整阅读与导航布局另行确认，不由同一布局机械缩放推出，也不擅自锁定屏幕方向。

## 5. 实现边界与未定事项

以下仅约束未来方案，不指定具体控件或公共 API：

- 保留场景设计坐标及其等比显示，UI 可用区域与 UI 基准比例分别处理。
- 视觉尺寸和触屏命中尺寸分别评估；不能只读取 FontSize 或设计画布中的按钮高度判断实际效果。
- 平台宿主负责可用区域与平台能力，主题负责排版；移动端适配不能扩大到 Editor、调试 UI 或所有宿主的全局样式。
- 优先复用现有导航、动作命令和设置服务，不为“更多”菜单复制一套状态或持久化路径。
- 明确仅场景截图、包含 UI 截图及缩略图的裁剪和分辨率策略，不在布局调整时隐式改变现有导出语义。
- 保留各主题独立设计，特别是 Minimal 的原有工具栏位置与 Paper 的侧栏布局，后续分别评审。

待对照稿确认：对白实际字号与高度、跨画布后的宽度上限、底栏常驻项目和菜单样式、不同方向的处理，以及 UI 基准比例与设备逻辑单位之间的换算。此时再形成具体实施 Phase。

## 6. 推进与验收顺序

### 第一步：原版基线与视觉对照

1. 采集 Classic 的桌面原版，并固定同一场景、人物和对白。
2. 提供桌面、手机普通横屏、手机超宽横屏对照稿，清楚标记画布边界、安全区域和真实显示尺寸。
3. 同时检查对白长短、长姓名、工具栏状态及“更多”菜单展开状态。
4. 用户确认视觉比例与观感后，再确定数值并开始代码实现。不先把方案扩展到所有页面和主题。

### 第二步：受控实现

只实施已确认的 Classic 游戏页切片，保留桌面回归截图。小范围通过后，再分别讨论设置页、其他主题和竖屏，不自动扩大本轮范围。

### 第三步：行为与真机验证

- 桌面对比原版的实际渲染尺寸、位置、留白和工具栏，不以相同的静态字号代替视觉一致。
- 场景比例与剧情坐标不变，对白和操作条可使用额外区域，且没有裁剪、重叠或文字溢出。
- 点击、触摸、菜单展开、返回、自动/快进状态和手势互斥正确，不误推进剧情。
- 检查下拉 popup、滚动视口裁剪、旋转、失焦及切页后的恢复，避免只测静态挂载。
- 核对截图与存档预览，分别记录实际执行和未执行的自动化测试。
- Android 真机确认字号、可触达性和系统手势避让；Headless 截图或测试通过不能替代实机体验确认。
