# 单项目 Sample UI 开发模板设计

状态：implementation；目标方案，按阶段实现。需求依据见 [feature.md](feature.md)。

## 2026-10-31 用户修订（优先于下文初版的主题保留设想）

取消 IGameLayoutTheme、GameLayoutTheme 与 Classic/Minimal/Paper 整套主题对象；不保留主题样式预设。内置层只保留配色、字体工具等可独立复用工具及控件必要的默认样式。应用字体选择、尺寸、布局、装饰及覆盖样式全部由唯一 Sample 项目拥有。Avalonia Styles/ControlTheme 是正常框架能力，不属于要移除的抽象。

GamePalette 保留独立语义配色资源及预设；Fluent 配色桥接可以作为配色辅助能力，不承担页面/模板选择。每套新应用设计以后以新模板提供，当前不开发第二模板或模板切换系统。下文提到使用主题，均落实为“默认控件样式 + 配色 + 项目应用样式”；P5 必须删除整套主题入口，不能以改名方式保留主题包协议。

用户授权逐阶段实现与提交。修订方案时尚无业务代码变更；P1 记录基线，P2 起执行机制解耦，后续结果记录于 execution.md。

P3 接口落点：`IPlayerApplication` 只连接应用表面、启动显示、语言选择和返回/退出策略；DI scope、初始化取消和释放仍由 AvaloniaPlayerHost 拥有。`IGameplayPage.State` 让通用 Shell 取得组合的呈现状态；GamePage 的 `Presentation` 属性独立于页面 DataContext。加载流程接收加载、游戏和失败呈现三个回调，不选择具体页面类型。Sample 在单一组合入口注册本项目 VM/View 和回调，不需要页面 VM 继承或服务别名。

迁移期间 DefaultPlayerApplication 与旧主题页面仅供尚未迁移的页面/测试接线，P4/P5 必须删除；不将它作为最终第二种 UI 模式。首次语言/确认/公告外观仍按 P4 迁移，本阶段不复制这些控件的实现到 Sample。

## 1. 核心决定

Sample 的默认页面就是开发模板，开发者复制后直接拥有页面和 VM。无需在“内置 UI / 自定义 UI”之间切换，也不维护两套对应页面。内置层提供复杂机制、控件与配色，Sample 决定交互、应用流程和应用视觉。

```text
Sample 应用项目
  App / Composition / Views / ViewModels / Styles / Localization / Assets
         │ 调用、组合、绑定
         ▼
内置层
  GameHost：内容与会话、持久化、平台生命周期
  GameView：游戏呈现状态、输入协调、页面呈现基础机制
  Controls：可复用控件与交互部件
  配色：语义颜色与预设；控件：必要的默认样式
         │
         ▼
现有 Runtime / Rendering / Assets / Storage / Media
```

这些是职责，不是新建程序集清单。优先沿用现有项目，不新建 ApplicationFramework、PageController 层或另一个共享 Sample 项目。内置层不得反向引用 Sample。

## 2. 当前实现与迁移原因

| 现状证据 | 问题 | 目标 |
| --- | --- | --- |
| `SampleCustomization.ConfigureServices` 调用 `AddAvaloniaGameViewPages(theme)` | 应用入口只有配置，缺少可编辑页面 | 一个集中组合入口注册本项目页面与 VM |
| `ClassicTitlePage` 内嵌 `Themes.Base.TitleMenu` | 增删常用按钮需要修改共享菜单或替换组件 | 标题按钮直接在 Sample XAML 中 |
| `IGameLayoutTheme.CreateStyles/RegisterViews` | 外观与整页应用组合耦合 | 删除主题协议；配色不选择页面，应用注册页面 |
| 默认页面注册检查固定的完整 VM 列表 | 删除可选功能仍须提供无用页面 | 检查启用功能和已声明导航，不要求固定全量页面 |
| `PageViewFactory` 按 VM 实际类型精确映射 | 派生替换需要同时处理别名和映射 | 项目直接注册自己拥有的 VM/View，保持明确映射 |
| `GameLaunchFlow` 直接跳转 Loading/Game/Title VM | 复杂加载过程绑死应用路由 | 准备/取消机制内置，导航编排由 Sample 决定 |
| `AvaloniaPlayerHost` 解析 PlayerView、Title/Game VM，处理应用返回 | 通用 scope 所有权与具体 UI 耦合 | 宿主持有生命周期，Sample 承接页面挂载及返回策略 |
| GamePage、GameRun、GamePresentation、Settings 依赖 GamePageViewModel | 移动 VM 会把运行状态机一起带走 | 抽取一个真实共享的游戏呈现状态对象，供这些消费者使用 |

以上按当前工作区核实；不能仅根据类注释或旧正式文档断言 Editor 还消费默认整页 UI。实施前补全真实引用清单。

## 3. Sample 所有权

唯一应用项目拥有：MainView/窗口布局、标题/加载/设置/存档/关于/鉴赏及详情页面、截图和确认布局、语言选择布局、游戏工具栏与覆盖面板组合，以及各页面 VM、导航与项目命令。

目录按普通 Avalonia 应用组织：`Views/`、`ViewModels/`、`Styles/Overrides.axaml`、`Localization/`、`Assets/`，一个 `Composition.cs` 集中组合。不强制改掉现有项目名称；重命名独立于行为迁移。

需要经常改的按钮序列在项目 XAML 展开。图片列表、设置字段、存档卡片等具有独立交互价值的控件仍可复用，但不能把整页按钮和业务流程封装成开发者无法局部编辑的黑盒。不要给每个 StackPanel 包一个框架控件。

平台入口仅处理平台初始化、路径、打包、窗口/Activity 挂载、生命周期转发；桌面窗口等应用 UI 仍集中于 Sample。保留平台必须的构建外壳及独立契约交付；不为追求物理单 csproj 牺牲跨平台能力。

## 4. VM 与内置机制边界

### 页面 VM

Sample VM 负责页面展示状态、项目条件、按钮命令、导航目标。例如新游戏前的角色选择、鉴赏入口过滤、打开项目扩展页均在这里直接编辑。普通 VM 使用现有 ObservableObject 或必要的导航基类，不继承内置 Title/Settings 等应用 VM 来获得替换资格。

### 内置机制

- 会话服务：内容初始化、准备/开始/恢复/停止运行、保存与 checkpoint、运行绑定和 scope 所有权。
- 游戏呈现状态：场景集合、对白/NVL/选项状态、等待完成、取消、自动/快进、历史和语音重播、交互阻塞。由一个 scope 内唯一对象拥有，不能在页面 VM 再镜像一套。
- 功能服务：存档枚举/缩略图与重命名、设置应用与持久化队列、鉴赏解锁与媒体/replay 释放、截图捕获/输出/安全路径与可释放预览等已有复杂能力。
- 可复用输入与呈现基础：返回历史、页面切换完成、输入监听及交互排除。基础导航不写死标题、设置等应用页面类型。

游戏页 VM 以属性暴露内置状态对象，并写自己的菜单命令；XAML 可以绑定该对象的集合、状态及播放命令。禁止为了维持旧绑定路径创建整套同名转发属性，也不为每条命令建立接口/Controller。具体状态对象名称在 P1/P2 确定。

复杂操作的异步正确性应由内置层保证。例如取消准备、替换旧运行及停止媒体不能依赖某个页面按钮恰好按正确顺序执行。页面编排只选择何时调用与下一步呈现什么。

## 5. 配色、控件和游戏页

配色负责语义颜色及必要的 Fluent 颜色桥接，不注册 View，不持有页面 VM 或导航。应用字体、间距、布局和样式归 Sample，控件库只提供必要的默认样式。资源作用域继续隔离于玩家根，不污染 Editor/调试窗口。项目局部资源优先；每个根创建独立 Styles，不共享已挂载实例。

默认页面迁移以 Classic 为基线，保持当前窗口、画布、本地化及交互行为。Ocean/Rose/Mono 等配色可继续复用；删除 Classic/Minimal/Paper 整套主题对象，不保留布局主题预设。以后新设计以新模板提供，当前不新增第二模板。

内置游戏承载控件继续拥有稳定 scene/presenter 实例，Sample 游戏页决定布局和工具栏。默认完整布局在 Sample 可见，不能为改工具栏复制一个隐藏的大模板。优先用已有内容槽和 ControlTheme 组合；仅在真实切片证明必要时补最小承载点，不建设通用 slot/插件框架。

保留场景、对白、NVL、选项承载校验及历史支持；同一内容只挂载一次。普通按钮等自动排除剧情推进，自定义交互区域有显式标记。运行中不任意重建持有打字/滚动状态的部件。全自定义外观仍须遵循这些运行契约。

截图、首次语言选择和退出确认的页面布局进入 Sample；预览/Bitmap 释放、取消、输入屏蔽与恢复等机制留在内置服务或有真实复用价值的控件。不要因为这些 UI 原来在 GameHost 就整类连机制搬走。

## 6. 组合接口与数据流

组合顺序：注册内置服务与一个游戏呈现状态 → 应用配色、内置控件默认样式与项目样式 → 注册项目 VM/View 和启用功能 → 建立 scope 并挂载 Sample 根视图。现有 registry/DI 可以继续用，默认全量应用注册拆除或收敛，不并行维护旧/新两套长期入口。

启动：平台入口提供路径/生命周期 → 内置宿主建立并初始化会话 → Sample 显示语言选择、启动状态或标题。

开始游戏：Sample 标题命令执行项目条件 → 显示本项目加载页 → 调用内置准备过程 → 挂载同一游戏承载控件并等待呈现完成 → 开始播放。失败、取消、回退到哪个页面由 Sample 明确编排；底层清理无论 UI 是否仍在都必须完成。

暂停/退出：平台或用户动作 → Sample 作页面/确认决策 → 内置暂停、落盘、取消和释放 → Sample 导航/关闭。Activity 重建只重挂载已有应用表面，不创建第二次运行。

内置机制需要 UI 协调时，优先现有事件、参数或小范围回调，不在宿主到处添加类型参数或页面服务定位器。只有真实所有权边界需要时才定义窄接口；接口不包含全部菜单和页面 ID。

## 7. 候选方案与取舍

| 方案 | 评价 |
| --- | --- |
| 继续主题整页 + 派生替换 VM | 改动少，但没有解决模板入口与替换成本，放弃 |
| 只把 XAML 放回 Sample | 可作为中间阶段，最终仍受具体 VM/宿主路由耦合限制 |
| 将整个 GameView/VM 原样复制到 Sample | 容易把状态机、媒体和输入机制变成项目负担，放弃 |
| 保留内置整页与项目整页双模式 | 重复维护、覆盖优先级增加，放弃 |
| 项目拥有页面/VM，内置拥有机制/控件/主题 | 采用；迁移需解除真实依赖，但定制路径最直接 |

开发者自行维护修改过的页面，后续新增官方按钮不会自动合并；内置机制修复仍通过升级获得。配色切换改变语义颜色，模板源码决定控件视觉与整页排列。这些取舍与源码模板目标一致。

## 8. 迁移与兼容

先建立现有功能/消费者基线，再提取呈现状态，接通标题到游戏的垂直切片，迁移其余页面和全局 UI，最后删除主题与旧入口。过渡适配只服务迁移，在最后阶段删除；不新增长期兼容模式。

旧页面 API 允许随本次源模板重构调整；实际消费者须迁移。PAK/契约、项目身份、玩家 profile、存档、语言回退、截图路径安全、发布布局及调试能力开关保持现有规则，不用清除用户数据解决迁移问题。

资源鉴赏当前工作区的新类型、scene replay、音频公告等作为基线保留；不能只迁移历史三套主题中的旧功能。跨平台及移动改版的历史未完成项单列，不能用本重构宣布完成。

## 9. 风险与验证

- 状态迁移导致双等待者、重复订阅或旧运行回写：验证准备取消、读档替换、scope 重建与释放顺序。
- 同页重挂载清空视觉树：验证实际窗口/单视图树与恢复后的输入，不只验证 VM 或进程存活。
- 页面拆分丢失交互契约：覆盖返回优先级、模态输入屏蔽、自动模式恢复、Gallery replay 停止和截图正式/预览区别。
- 配色/字体/文案作用域改变：验证默认布局、局部覆盖、长文案/中英文、真实本地化关闭/重开。
- 以模板可扩展性为名新增过多接口：以仓库外真实定制探针衡量，常见自定义不能要求修改内置源码。

验收分为机制回归、挂载/控件渲染、真实宿主与仓库外定制四层；headless 不能代替真实媒体、平台生命周期和发布验证。执行顺序和退出条件见 [phase-plan.md](phase-plan.md)。正式 spec/manual 只在对应实现验证后更新。
