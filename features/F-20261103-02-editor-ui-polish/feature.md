# Editor UI 与配置体验优化

状态：in-progress（P0–P4 进行中）
创建日期：2026-11-03

## 用户原始目标

> 优化Editor的UI，先设计，比如我想到的点有：  1. 所有窗口右上角的三个按钮没有单独背景色，hover和点击有就够了 2. 编辑器设置页面和项目设置一样分页，且快捷键不要有应用按钮，参考sample的绑定功能，自动更新，保留一个重置就行，重置也用类似其他面板的icon button, 两个面板默认尺寸宽一点，排版、对齐再优化，目前还是太丑了，有些比如音频什么的可以定制编辑UI，很久以前那个都比现在的好看，最后就是不要有直接修改json的，复杂结构都要有自己的配置UI或者扁平展开  3. 文件页面图片有预览就不要那个背景icon 了，会重叠显示  4. 优化一些右键菜单的选项排列  5. 问题面板不要有技术详情的expander，点击一个项后inspector显示就行。还有什么点吗

用户补充：颜色有点单调，部分视觉不明显，但也不要使用太多颜色。

## 当前问题与范围

- 窗口右上角最小化、最大化/还原、关闭按钮常态不应有各自的背景色；保留悬停、按下反馈。
- 编辑器设置参照项目设置分页；快捷键参照 Sample 绑定体验，自动更新，移除应用按钮，每个快捷键保留一个重置并采用与其他面板一致的图标按钮；保留全部重置，执行前确认。两个设置面板默认更宽，改善整体排版与对齐。
- 检查并改善设置中的复杂字段，音频等适合领域化交互的内容考虑专用 UI；Editor 用户接触到的配置尽量避免直接编辑 JSON；复杂结构应有配置界面或扁平展开，参考 Entry 参数、Transform 等既有设计。异常数据和未知扩展的处理需进一步调查。
- 文件页已有图片预览时不显示叠在其后的类型图标；没有可用预览时仍需有可识别的文件表示。
- 改善颜色和视觉层级，使重要信息及交互状态更容易辨认，控制颜色数量，避免界面过于花哨。
- 审视右键菜单的选项排列、分组与一致性，具体范围和顺序在设计时结合实际场景确定。
- Problems 列表不再内嵌技术详情折叠区；单击问题在 Inspector 显示详情，双击跳转到问题位置；保留草稿处理能力。

## 已观察到的现状

- 编辑器设置目前为单一滚动页；快捷键每项有文本框、应用和重置按钮，另有全部重置。项目设置使用左侧分页。以上为源码静态观察，未作桌面视觉验收。
- 文件网格模板同时绘制类型图标与缩略图；Problems 行内包含详情 Expander，定位目前通过行内按钮触发。
- 现有图集契约对未知字段或坏结构保留原文并禁止类型化改写，文档允许通过通用文件入口修复。新的 JSON 要求与此存在需要明确的边界，不能以隐藏入口代替数据保护。

## 整体检查方向

- 通过文字层级、间距、边界与少量语义色区分标题、正文、次要信息及选中、焦点、错误状态；先检查主题间对比度和信息密度。
- 设置、资源和问题面板检查空状态、长内容截断、当前选择，以及保存/自动更新反馈，避免仅用颜色传递状态。
- 右键菜单按操作语义分组，把删除等破坏性操作与常用操作分开，并核对空白处、文件和多选时的作用对象及禁用状态。
- 设置页关注窄面板、长翻译和不同字号下的换行、滚动及对齐；图标按钮提供提示和无障碍名称。
- 快捷键录入需明确冲突、无效输入和取消行为；问题详情需考虑无定位目标、Inspector 锁定及选择后原有导航行为。
- 音频等专用 UI 和其余直接 JSON 编辑入口先做清单，区分常规已知结构、扩展结构和损坏数据，再确定覆盖范围与兼容方式。

用户确认整体考虑这些方向；具体调整以盘点和设计验证为准。

## 非目标

- 阶段计划不等于业务代码已实施。
- 暂不假定重做整个 Editor 的视觉体系、修改项目数据格式或改变运行时语义。

## 初步验收标准

1. 相关窗口的三个标题栏按钮常态无独立背景，悬停及按下有清晰反馈。
2. 编辑器设置分页；快捷键修改可自动生效，无应用按钮，每项重置使用一致的图标交互；设置面板默认宽度、排版和对齐经过实际验证。
3. 纳入范围的复杂配置不要求直接编辑 JSON；已知与异常数据的具体覆盖、数据保全和修复体验经确认后验收。
4. 有效图片缩略图与类型图标不重叠，无预览时仍有可识别表示。
5. 纳入范围的右键菜单次序、分组和操作对象清晰一致。
6. Problems 项不内嵌技术详情 expander；单击问题后 Inspector 显示详情，双击跳转到问题位置，草稿操作不丢失。
7. 重要信息与选中、焦点、错误等状态清晰可辨，配色克制且不同主题下保持可读。
8. 实际检查常见窗口尺寸、主题和语言，并验证快捷键、选择、定位、配置保存及既有数据保护；具体测试矩阵由设计确定。

## 约束

- 优先复用现有控件、绑定、项目历史与保存机制，避免为局部视觉调整引入额外复杂度；保留取消、清理及资源所有权保证。
- 遵循仓库本地开发约定，额外验证产物放在 `output/`，不提交 Git；遇到文件占用、环境冲突或需隔离环境时先与用户确认。
- 保持已有项目内容、未知字段与扩展兼容；不可静默覆盖或丢弃无法识别的数据。

## 假设与开放问题

- “两个面板”暂理解为编辑器设置和项目设置；默认宽度是初始布局需求，保留用户已有布局的行为待设计核实。
- 用户确认每个快捷键保留一个重置；全部重置也保留，并在执行前弹窗确认。
- 用户确认 Editor 用户接触的内容尽量不用 JSON，参考 Entry 参数和 Transform 的结构化设计；需要盘点通用文件入口、未知扩展与损坏配置，并设计无损处理和修复体验。
- 用户确认问题单击显示 Inspector 详情、双击跳转；沿用 Inspector 现有锁定语义，不增加特殊提示或解锁流程。
- 右键菜单和配置入口先整体盘点，再按实际场景确定调整；不能以静态搜索替代覆盖证据。
