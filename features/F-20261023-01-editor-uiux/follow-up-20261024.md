# 首次使用反馈

原 UIUX 已先提交为 `d93bf52`（97 个文件）。原有其他 feature 修改及临时格式清单未纳入。以下为提交后的后续处理。

## 1. 按钮 hover 迟缓：仅分析

本轮没有改动 hover 实现。检查仓库样式，并通过 Headless 挂载读取已安装 Semi 12.1.0 的实际 ControlTheme 状态树与 VisualTree；临时诊断代码已移除，原始输出在忽略的 `artifacts/uiux/semi-hover-source.txt`。

确认的事实：

- 普通 Button/ToggleButton 自身与模板 `PART_ContentPresenter` 都有背景/边框过渡，160ms、Delay=0、LinearEasing。Semi hover 直接修改 ContentPresenter；ToggleButton 的 checked 基础态修改外层 Background，checked-hover 又修改 ContentPresenter。
- EntryTypePicker 的 OpenButton 是上述 ToggleButton。条目折叠箭头则使用自定义图标 ToggleButton，其高亮在 ButtonSurface Border；需要区分两条路径，不能因为都叫“展开按钮”就使用同一结论。
- TextBox 的 hover 主要作用于 `PART_ContentPresenterBorder`；MenuItem 的可见高亮主要作用于 `PART_LayoutRoot` Border。两者同样是 160ms、无 Delay，但更接近单个绘制表面的状态变化。
- 普通按钮的 Fill0→Fill1 背景变化与 TextBox 边框反馈对比不同。以 Violet 为例，前者为 #313244→#45475A；较弱的早期变化可能被感知为“停了一会儿才亮”。

推断与待证实部分：重复动画层及模板绑定在 checked/pressed/hover 交接时可能产生追逐或重启过渡；普通 hover 直接写 ContentPresenter 时并非必然经历两次串联过渡，不能简单断言所有按钮都变成 320ms。还没有真实桌面帧时间证据，不能将其定性为 UI 线程卡顿。

建议后续先统一“只由一个实际绘制表面负责过渡”，明确 normal/hover/pressed/checked 的状态优先级，再与 TextBox 对照实际中间帧和快速进出；保留预乘 alpha 防闪白。不要仅缩短时长或关闭动画后宣称修复。
