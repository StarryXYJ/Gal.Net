# 游戏 UI 主题与配色设计

状态：Implemented，2026-10-11，关联 [F-20261011-01](../../features/F-20261011-01-game-ui-themes/feature.md)。当前契约以 [control.md](../spec/control.md) 和 [Themes README](../../src/Presentation/GalNet.Avalonia.Themes/README.md) 为准。以下保留初始设计分析，候选项不自动成为实现承诺。

## 落地决定与初始设计差异

- 单一可选 GalNet.Avalonia.Themes 项目，Classic/Minimal/Paper 布局和 Ocean/Rose/Mono 独立配色；Sample 默认 Classic + Ocean。
- 启动代码通过 IGameLayoutTheme 同时提供 Styles 与页面注册，GameShell 自动加载资源；未提供直接的主题 XAML 元素、运行期选择器或继承/ID 注册系统。
- 普通页保留 View + ViewModel；内置布局覆盖标题，其余页面共享资源化的基础 View。GamePage 成为稳定 TemplatedControl，以 Scene/Dialogue/Nvl/Choice 四个内容属性和 PART_* ContentPresenter 安排布局。
- 注册顺序为默认→主题→宿主 Gallery 回调→宿主普通回调，最终 View 自动补充 Scoped 注册。游戏页自定义类型须继承 GamePage，确保 Runtime 与页面工厂使用同一实例。
- 玩家根内使用 Fluent，基础色桥接至所选语义配色；宿主 Semi 与编辑器隔离。截图弹窗显式引入相同主题。当前 Sample 的确认/通知属于调试功能，沿用宿主外观。
- 固定美术可以保留；Paper 标题的原创矢量纹理使用固定棕色，交互与文本跟随配色。
- 配色目前包含 21 个必需画刷，未实现下述所有扩展状态键。九种组合在 1280×720 headless Skia 渲染并验证输入及截图；原生媒体、系统对话框、全 DPI/字体环境未纳入该测试。

架构取舍记录于 [ADR 0003](../adr/0003-startup-game-layout-themes.md)。

## 目标与范围

保持 GalNet Avalonia 控件的行为可复用，为开发者提供覆盖主要玩家界面的参考主题。第一版由开发者在代码/XAML 的应用组合期配置主题与配色，运行中保持固定。用户已明确先取消动态主题切换；不实现玩家变量绑定、运行期主题选择器或安全边界切换协调器。配色保持独立资源结构，热切换配色不作为第一版验收要求。

覆盖标题、加载、游戏对白与 NVL、剧情选择、游戏工具栏、存读档、设置、全部内置鉴赏页面、关于、截图和应用确认/错误弹窗，以及 Sample 首次语言选择和启动状态。调试窗口、编辑器自身 UI、操作系统文件选择器不属于游戏主题覆盖范围。Sample 窗口客户区属于覆盖范围，原生窗口装饰由平台宿主决定。

主题不决定游戏内容、导航可用性、存档格式、媒体后端、玩家变量语义或业务执行。Core/Runtime 不依赖主题系统。剧情明确指定的文本颜色、场景图像与效果仍属于游戏内容，不自动改成 UI 配色。

## 已验证的实现基础与缺口

- `GalNet.Avalonia.Controls/Styles/Generic.axaml` 已有对白、选项、存档卡和 NVL 模板，但含固定色值和尺寸。
- `GameShell` 和页面有本地视觉值及局部样式；主题迁移需要主动清理这些决定，不能只在 App 末尾追加样式。
- `PageViewRegistry` 在组合期构建后不可变；`PageViewFactory` 从游戏 Scope 解析 View。默认页面 View 与 ViewModel 均为 Scoped，现有工厂不会为外观变化自然创建新实例。
- `AvaloniaGamePresenters`、Sample 会话与 presentation 直接依赖具体 `GamePage`。`GameShell` 截图路径也把当前内容转换为 `GamePage`。
- `GamePage` 具名元素承担渲染、对白与输入接线；对白运行状态保存在 `TypewriterTextBlock`，NVL 历史保存在模板内部的行容器。保留 ViewModel 或外层控件实例不足以保证重新应用模板时保留这些状态。
- Sample 首次语言选择与启动状态位于 `GameShell` 之外，需要独立接入同一个外观上下文。
- Sample App 同时引入 Semi、UrsaSemi 和 Fluent。游戏 UI 必须明确基础控件主题与隔离方式，不能依赖多个基础主题的偶然加载顺序。

当前页面边界见 [control.md](../spec/control.md)。

## 外观模型

### 基础色表

提供原始颜色及色阶，例如 `GalNet.Color.Blue.500`、`GalNet.Color.Neutral.900`，不包含控件或业务语义。色表可扩展，配色也允许直接使用自定义颜色；不强制所有色值来自官方色表。

### 语义配色 Palette

将原始颜色映射到用途，建议包含：

- Primary、Secondary 及 Hover/Pressed/Disabled 状态。
- Success、Warning、Error、Info 及对应前景与柔和背景。
- Background、Surface、SurfaceRaised、Overlay。
- TextPrimary、TextSecondary、TextDisabled。
- OnPrimary、OnSecondary，确保强调背景上的文字有明确配色。
- Border、Divider、Focus、Selection。

区分 Color 与 Brush 的资源类型，例如 `GalNet.Palette.PrimaryColor` 与 `GalNet.Brush.Primary`。不使用字符串资源冒充颜色，不在不支持动态引用的位置假设资源别名可以自动追踪变化。迁移时以真实 Avalonia 12 页面验证“基础色 → 语义色 → Brush → 控件”的更新链路。

配色提供完整语义资源。Light/Dark 属于配色维度，不应混同完整布局主题；第一版配置具体配色资源或对象，不要求建立运行期 ID 注册表。

### 视觉主题 Theme

提供控件模板、普通页面 View、游戏布局、背景图与纹理、字体、间距、圆角、装饰和动效。模板对需要跟随配色的值使用动态语义资源。

视觉主题可以选择纯色、图片或混合背景，也可以固定部分美术颜色。公共配色的采用范围由主题说明：完整、部分或固定美术配色。主题推荐一个默认 Palette，但显式选择 Palette 时不得偷偷覆盖请求。

主题可定义专用资源，例如 `GalNet.Theme.Dialogue.Surface`、`GalNet.Theme.Title.BackgroundImage`。专用颜色默认可以引用语义配色，也允许固定颜色；图像和字体不属于 Palette。

AppearanceVariant 不作为第一版必需的第三选择轴。二周目外观与其他运行期变更先留作后续需求，不为其预建选择机制。

## 模块与资源作用域

- Controls：行为、模板契约、最小可用的中性基础模板；保持独立引用能力。
- GameView：共享 ViewModel、导航、稳定游戏宿主、页面与模板契约、组合期页面注册。
- 官方内置主题集合项目：建议新增 `src/Presentation/GalNet.Avalonia.Themes`，集中提供内置布局主题、页面 View、控件模板、配色和主题素材，依赖 Controls/GameView；共享层不反向依赖它。Sample 与其他宿主按需引用该项目。第一版不按每套主题或配色拆程序集。
- Palette：在主题集合项目中独立组织，不嵌在某套布局主题目录内。布局主题与配色不是一一对应关系，可独立组合。
- Sample/其他宿主：在组合期配置主题与配色、覆盖页面并提供平台能力。

建议目录结构（名称均为设计提案）：

```text
GalNet.Avalonia.Themes/
  Colors/             # 原始色表
  Palettes/           # Ocean、Rose、Mono 等完整语义配色
  Base/               # 公共视觉资源与可复用模板
  Layouts/
    Classic/          # 页面、控件主题、主题素材
    Minimal/
    Paper/
  Composition/        # 引入资源与组合期页面注册入口
```

主题集合只是官方实现的容器，不承担游戏执行逻辑。第三方可以另建项目，使用共享的控件/页面契约，无需引用官方主题集合；仅需要复用官方色表或模板时才引用。以后出现包体或发布节奏需求再拆项目，不先创建 Themes.Abstractions 或每主题一包。

组合举例：Classic + Ocean、Classic + Rose、Minimal + Ocean。各布局依赖相同语义键，不读取配色名称或限定其目录路径；布局推荐配色只是默认值，不是绑定关系。固定美术区域可以不跟随配色，其支持范围需在 README 中说明。

应用内每个独立游戏/预览根使用明确的游戏资源作用域，避免样式污染其他预览或编辑器。Sample 的启动页、语言选择页和后续 GameShell 使用同一份外观配置，不依赖玩家存储就绪。第一版不需要可变 AppearanceContext 服务。

资源逻辑优先级从低到高为：基础必需资源 → 已配置的完整配色 → 已配置的主题专用资源 → 宿主覆盖。公共语义配色键与主题专用键分开，主题不得以重定义公共 Palette 键的方式绕过宿主配色配置。

该优先级是目标契约，必须通过资源结构和实际查找路径实现并验证；不能假定不同字典层级的加载先后等于优先级。

弹窗、Popup、独立截图窗口等可能有不同的资源查找路径，需要显式接入相同的外观资源。原生文件选择器采用系统外观。

## 页面与控件扩展

### 普通页面

标题、设置、存档列表、鉴赏入口、关于等采用共享 ViewModel + 主题 UserControl。主题可只覆盖部分页面，其余沿用基础主题；不要求所有页面改成 TemplatedControl。

页面 View 负责视觉与绑定，不复制加载、保存、导航或变量逻辑。必要行为通过稳定命令与宿主服务暴露。长文本、动态本地化、禁用状态和未知鉴赏类型仍必须可用。

ViewModel 与默认页面 View 可沿用现有游戏 Scope 生命周期。没有动态切换，不需要新增按主题缓存、View 热替换和视觉状态迁移机制。

### 游戏与有媒体状态的页面

推荐将 GamePage 本身改为外观中性的 TemplatedControl，而不是让每个主题提供另一种 GamePage 类型。名称可沿用 GamePage；不要求额外包装一个 GamePageHost。

共享 GamePage 保留场景渲染、输入路由、presenter 接线和截图能力。运行实例拥有 Scene、Dialogue、Nvl、Choice 等核心内容控件，主题通过 ControlTheme 的布局模板及有限 ContentPresenter 承载点安排它们；工具栏绑定共享 ViewModel 的命令。主题不创建第二套游戏 presenter，也不拥有 Engine 或媒体服务。

该内容插槽方案与“模板直接创建全部核心 PART 控件”相比，需要少量额外内容属性，但减少主题对核心控件类型与接线的重复。第一版采用内容插槽方向，具体属性和部件名在 feature 设计时确定。

在初始化/模板就绪阶段验证必需内容已挂载，成功后才允许首条对白执行。保持基础可用模板；宿主替换成损坏模板时给出明确诊断。

现有 presenter 与 Sample 可继续依赖这个稳定的 GamePage 类型，只调整具名字段访问为稳定内容属性。截图也继续调用其场景截图能力。只有确实需要允许替换整个游戏宿主实现时才增加接口，第一版不为主题专门增加这一层。

同一内容控件只能有一个父节点，主题模板不得把同一个场景或对白插槽显示两次。页面导航仍复用同一游戏实例，不因换页重新创建 presenter。取消动态切换后，不需要支持运行中跨模板迁移。

Gallery 视频/音频播放页仍需分离共享播放行为与主题外观，但可在组合期决定 View。复用既有媒体服务，不复制播放生命周期，不为第一版增加运行期替换机制。

游戏输入应根据明确的交互区域/消费状态决定是否推进，不能只识别 Button 或 ChoiceList。主题新增 Slider、TextBox 等交互内容时不得误推进剧情。

### 控件模板契约

保留并文档化 `PART_Typewriter`、NVL 行容器与滚动容器等现有必需部件。缺失部件给出明确诊断，不能把待完成对白静默判为已完成。

基础模板保证键盘焦点、禁用/选择状态和行为可用。主题的模板变更可改变结构，但不能改变完成语义。若以后支持运行中重新创建打字机/NVL 内部部件，需先把进度、历史和完成任务生命周期从模板部件移到独立呈现状态。

## 注册、回退与兼容性

在组合期选择一套主题，装配其资源、ControlTheme 和普通页面 View 映射。沿用现有不可变页面注册表及 PageViewFactory，不增加主题感知的运行期 View 工厂。

页面注册顺序为基础页面 → 所选主题覆盖 → 宿主显式覆盖，最终映射在启动完成前固定。现有宿主页面覆盖保留优先权。主题需要同时支持 XAML 样式引入和代码侧页面注册；具体统一配置入口在 feature 中确定，避免开发者只引入样式却漏掉页面映射。

主题可以声明一个基础主题；第一版优先单层继承。部分主题未提供页面/专用资源时允许回退，循环继承与重复 ID 在注册时拒绝。

区分“可选覆盖缺失”和“声明的实现损坏”：前者回退，后者诊断并拒绝初始化，不能通过静默回退掩盖绑定或模板错误。Palette 必需键在初始化时检查。

包内引用主题即可；第一版不加载任意目录下的 XAML/程序集作为运行期插件。主题包说明默认配色、覆盖能力与模板契约；不需要为配置类额外建立运行期主题 ID、选择状态和偏好存储系统。

## 配置与后续扩展边界

第一版配置流程：开发者选定主题与配色 → 引入主题资源 → 注册主题页面覆盖 → 宿主追加定制 → 构建游戏 Scope → 验证并显示 UI。

配色和主题独立配置；未显式提供配色时使用主题默认配色。样式继续通过资源引用获取颜色，使用 DynamicResource 不意味着库承诺运行时完整主题切换。

取消 ThemeId/PaletteId 绑定、外观协调器、Applied/Pending 状态、安全边界检测和热替换 View。二周目等需求若以后恢复，应单独分析：启动前条件选择和游戏运行中切换是不同能力。启动前读取玩家数据也是宿主责任，不作为本期配置流程要求。

动态主题切换的历史风险保留在事实说明中：当前对白/NVL 状态与模板部件耦合，未来恢复该能力时必须重新设计和验证，不能把本期可替换模板视为任意时刻重建模板的保证。

## 示例与开发者体验

拟提供 Classic、Minimal、Paper 三个示例，体现不同布局和背景策略，不只是三套换色。每个示例可引用共享的基础页面与模板，避免机械复制整个 UI。示例素材具备可再分发与二次开发许可。

Sample 外观展示入口包含所有页面、ADV/NVL、长文本、选项、存档空/正常/损坏状态、设置控件、应用弹窗以及键盘状态。UI 文案继续使用已有本地化机制，字体需考虑中文等 fallback；宽高采用容器约束与可滚动布局，验证现有最小窗口、DPI 与长文案。

README 分别示范代码/XAML 配置、仅覆盖配色、仅替换一个页面以及基于基础主题修改。标明主题哪些区域跟随 Palette、哪些属于固定美术。展示多个主题可用不同启动配置，不要求运行期选择器。

## 候选方案与取舍

- 只抽资源：成本低，可换色，无法覆盖主页面结构；不满足目标。
- 所有 Page 模板化：统一外观入口，但扩大部件契约并增加简单页面的开发负担；不采用为通用要求。
- 每套主题复制所有 Page 和 code-behind：自由度高，但复制业务与媒体生命周期；不采用。
- 普通 View 在组合期替换 + GamePage 本身布局模板化：保留开发自由并集中生命周期，是推荐方向；代价是把现有 GamePage 的视觉树移入模板并暴露稳定内容属性。

## 验收与实施顺序建议

1. 最小原型验证游戏根资源隔离、配色资源链、Popup/弹窗资源路径及单一明确基础控件主题。
2. 抽取公共资源和稳定游戏宿主，清理本地视觉硬编码，完成一个主题覆盖全 Sample。
3. 完成组合期主题页面注册与回退，保留原宿主页面覆盖能力。
4. 制作布局不同的其他主题、配色、展示入口与开发者配置示例。

验收重点：不同启动配置能覆盖主要玩家界面；首条对白等待模板就绪且正常阻塞；NVL/选项/输入推进行为不受布局影响；同页导航重挂不出现双父节点；截图与媒体仍可用；语言选择、弹窗与正文 UI 配色一致；游戏根之间不串资源；宿主覆盖与缺失回退结果确定；会话正常释放事件订阅与图片资源。

## 需要确认的产品选择

- 视觉主题对 Palette 的支持是否允许部分/固定？推荐允许并明确能力，官方示例至少包含完整采用配色的主题。
- 是否单独要求运行时配色切换？当前按组合期固定配色处理，语义资源结构保留，但不增加切换 API。
- 默认样例主题与配色，以及三个参考主题的美术方向尚未确认。
- 官方集合项目建议统一为 GalNet.Avalonia.Themes；公开配置 API 名称、基础控件主题策略和兼容版本策略待 feature 中细化。
